# ADR-0019：审批收敛（C：计划级审批）

- 状态：**C1 + 档位优先 + C2 全链路代码已落地；手机计划卡点击待真机验收**（2026-11-12）
- 日期：2026-11-11
- 关联：ADR-0012（权限档位）、`docs/task-approval-convergence.md`、`packages/policy`

## 背景

`workspace` 档原来对工作区内的写/删/脚本直接放行，只在时间线留一条
“已自动放行（免问）”。结果：动作先做了，人才知道；控制塔的“待你决定”不可信。

用户选择 **C（计划级审批）**，目标：

- Agent 先交计划（将改哪些文件、跑什么脚本）
- 人批计划
- 计划内自动
- 计划外再问
- 硬禁止永远不放

## 决定

### C1 计划外先问（已落地）

- `policy` 的 `workspace` 档：
  - 读：自动
  - 工作区内写/删/脚本：`ASK`
  - 工作区外：`ASK`
  - `full` / `read-only` 行为不变
  - 硬禁止不变
- 启动器在用户批准后，把“本轮同类”（`grantKey`）放进 `turnGrants`；
  同类第二次起自动；换任务/换一轮重新问。
- UI 权限档位文案改成“工作区内写/脚本先问一次，本轮批准后同类放行”。
- 测试：policy 22 条通过；原来的“直接放行”用例改成“先问”。

### C2 计划内自动（全链路代码已落地）

**已实现：**

1. **host 协议（C2.1）**
   - `POST /plan`（token）：接收 `{title?, steps[]}`，创建 `plan_<id>`；
     每步只收 `kind / action_display / facts`，最多 50 步；返回 `plan_id / expires_at`
   - 计划归属当前活动会话；`plan_request` 推给手机，并进入流水
   - 计划必须至少有一个具体目标（writes/deletes/script/files 中的真实路径）；
     只有“整理一下”“清理一下”的计划直接 400 `plan-needs-target`，不生成空计划卡
   - `GET /plan/:id`（token）：查询 pending/allowed/rejected/expired
   - `POST /plan/decision`（token）：`allow` / `reject`；非当前会话 409，
     已决策 409，过期 410；发 `plan_decision`
   - 手机晚连上 / resync 会补发未决策计划；过期计划按 5 分钟 TTL 标记
   - `full` 下提交计划自动 allowed，不把人卡在手机上
2. **Agent 提交计划（C2.2）**
   - MCP 工具 `vance_plan`：参数 `steps[]`，每步含
     `kind / action_display / facts`（writes/deletes/script/program）
   - 工具 POST 到 host `/plan`，带主 token；轮询到 allowed/rejected/expired 才返回
   - `AGENTS.md` + 每轮提示都要求：写/删/跑脚本前先调用；返回非 allowed 不执行
3. **手机计划卡（C2.3）**
   - 列出“将要改哪些文件 / 跑哪些脚本”，按钮：拒绝 / 批准计划
   - 批准后显示“计划内自动，计划外再问”
   - 计划待批时算进“待批”，输入框锁住，和审批卡同一套轴
4. **计划内/外判定**
   - host-demo 保存已批准计划的**具体目标路径**（不是目录、不是程序名）
   - `classifyApproval` 先跑：硬禁止仍拒绝；`full` 自动；`read-only` 不放宽
   - 仅 `workspace` 下，动作的**每个**目标路径都在计划里 → 自动放行
   - 任一目标不在计划里，或 facts 拿不到目标 → 回到 C1 弹卡
   - 计划有 5 分钟有效期；换任务/停止/拒绝清空计划 grants\n   - 移动必须用 `facts.moves:[{from,to}]`；host 按用户策略检查批量上限/禁止根目录；批准后写撤销清单，`POST /undo/:plan_id` 可撤回
5. **验证**
   - host 50、web 18、全量 156
   - 真实 Agent 端到端：Agent 调 `vance_plan` → 计划卡 → 批准 → 写文件时**不再弹写入审批**
   - 真机手机点计划卡还没人工验收（下一步）

**仍未做：**

- 手机真机点“批准计划/拒绝”的视觉与交互验收（代码/单测已过）
- 计划变更后强制重新批（当前是旧计划到期/换任务失效）
- 计划模板、多 Agent 计划合并
- `read-only` 下的计划卡文案还可以更明确（不能放宽）

## 与权限分层的关系（2026-11-11 拍板）

**计划不是第四种权限档，是档位天花板下面的一张任务内通行证。**
判定顺序固定为：

1. **硬禁止**：直接拒绝，不是问；任何档位/计划/旧规则都不能放。
2. **权限档位天花板**：
   - `full`：非硬禁止全自动；计划不需要，Agent 若提交计划则自动通过（不弹卡）。
   - `read-only`：写/脚本一律问；**记住的规则和计划都不能放宽**。
   - `workspace`：允许计划内/记住的规则免问。
3. **计划 / 记住的规则**：只在 `workspace` 内生效。
4. 都没有覆盖：弹卡问人。

因此：

- `full` 不会因为计划或记住的规则多问一次；只受硬禁止约束。
- `read-only` 不会因为旧白名单或计划被偷偷放宽。
- 切换档位时清空**计划 grants**；记住的规则还留着，但只在 `workspace` 生效。

当前 `packages/policy` 已按此顺序落地（记住的规则从 read-only 之前挪到了之后）；
`policy` 测试 22 条。host-demo 的计划 grants 也按这个表接好了。

## 为什么先 C1

没有 C1，C2 只是装饰：Agent 不交计划时仍然自动写；计划外也没有“再问”的基线。
C1 让“计划外”真的会停下来，C2 才有意义。

## 后果

- 现在 workspace 写/脚本会多一次打断；批准后同类不再问。
- `full` 是显式长期状态：跨轮、跨重启保持，直到手动切回；切到 `full` 时，
  已经挂起的非硬禁止审批自动批准（`by=auto-full`）；硬禁止不变。
- C2.1 协议已落地；MCP 工具、计划卡、计划 grants 未做，**未实现前不要声称“计划级审批已完成”**。
- 计划审批不是“AI 摘要”；计划步骤来自 Agent 的事实/动作，人批的是具体动作。

## 没做什么

- 手机真机点计划卡还没人工验收；目前只做了单测/构建和真实 Agent 自动流程。\n- 撤销清单目前是 host 侧 JSON + 接口，手机 UI 还没接。
- 没有做计划模板/计划变更重批。
- 没有做多 Agent 的计划合并。
