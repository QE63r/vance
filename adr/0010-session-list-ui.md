# ADR-0010：任务列表与规则撤销（第一刀）

- 状态：已接受
- 日期：2026-11-06
- 关联：ADR-0008（会话身份）、ADR-0009（审计与产出）、（内部任务卡已移除）

## 背景

`session_id`、`/sessions`、`/rules` 都已在协议里，但手机上没有入口：
切会话只能改地址，规则撤销只能用 curl。设计稿里的列表屏 / 设置屏是完整形态，
这一刀只做**能被手指碰到的最小版**：一个菜单、两个面板。

## 决定

### 一、入口是顶栏 `⋯`，不是路由

顶栏右侧加一个按钮，打开底部面板（复用现有 `sheet` 样式），面板里两项：
「任务列表」「记住的规则」。不引路由库、不做底部 tab、不做独立设置屏。

理由：三张屏是最终形态，但现在只有两件事需要入口；先让手指够得着，
再谈信息架构。代价是 `⋯` 里以后会长出更多项，届时再拆设置屏。

### 二、切换用 `session/attach`，不重连

手机发 `{ type:"session/attach", sessionId }`；host 把**这条连接**的观看会话
改成目标，回一条 `session`（标题 / 是否 active）+ 该会话 `history` + 该会话 pending 审批。

- 只改"看哪条"，不动 host 的执行会话：正在跑的任务不会被切走、也不会停。
- 未知 id：只回 `notice`，不改观看会话（和 `?session=` 的未知处理一致）。
- 切换时 `history` 会清空重建（现有行为），审批与执行轴由回放重建。

为什么不做"重连换 `?session=`"：重连会走退避、断线闪烁，也会丢掉当前连接的
pending 审批补发时机；一条消息能解决的事不该用连接生命周期解决。

### 三、列表与规则都直接读现有接口

`GET /sessions`、`GET /rules`、`POST /rules/revoke`。不新增接口、不缓存到 store：
面板打开时拉一次，撤销成功后就地删掉那一行。

规则 key 暂时原样显示（如 `remove-item|desktop`）。人话化（"删除 · 桌面"）
留给体验债那张卡——现在还没想清楚 `treatKey` 的几种形态怎么统一展示。

### 四、store 只加一个字段

`State.sessionId`：`hello` 与 `session` 都更新它，面板用来标"正在看"。
不引入 S 轴全套（activeId / openedId / list），那是完整列表屏的事。

## 后果

- 手机能点着切任务、能撤销规则；旧账 `legacy` 自然出现在列表里，不用记地址。
- 切换是只读视角：切到历史任务不会停止当前执行。
- 测试 118 → 120（`session/attach` 两条 host 用例；web 的 hello/session 断言并入空会话用例）。
- 已用 390×844 无头浏览器验过：菜单 → 列表 → 切到 legacy → 规则撤销，服务端数组同步减少。

## 失效条件

- 若列表要显示"每条的未读数 / 最后一条消息预览"，`GET /sessions` 的字段不够，
  本 ADR 第三条作废。
- 若以后允许多会话**并发执行**，`session/attach` 只改观看会话的语义仍成立，
  但"单 active"前提消失，需要补"这条在跑吗"的每会话状态。
- 若引入路由，`⋯` 入口应换成正式导航，本 ADR 第一条作废。
