# ADR-0004：不做 AI 意图摘要，改用「步骤流」

- 状态：已接受
- 日期：2026-11-02
- 关联：ADR-0002（信封）、ADR-0003（成本）

## 背景

审批卡片的第四行原本是「AI 推测意图」：用模型把一条命令翻译成
"它大概想干什么"。

三个问题：

1. **要花钱**，且成本随审批次数线性增长（ADR-0003 已定性为结构性风险）。
2. **可能猜错**。命令是删 `data.csv`，摘要可能写成"清理临时文件"——
   人会据此批准一个自己没看懂的动作。
3. **价值被高估**。从 `tool.kind`、`locations`、参数就能拼出确定性的
   「事实句」（"删除 1 个文件：data.csv"），已经够做判断；模型多给的只是"为什么"，
   而"为什么"恰恰最不可靠。

## 决定

### 一、删除 `intent_summary`

schema 里不再有这个字段；带上它的事件会被判为非法（审批类事件是 strict 的）。

### 二、以「步骤流」作为主要可观测对象

用户真正需要的是：**它刚才做完了什么、现在在做什么、下一步是什么**。
这不是"解释意图"，是"显示进度"——而进度是确定性的，不需要模型。

用 `StatusUpdate.step` 承载：

```ts
step: { id, title, kind, status: "pending" | "running" | "done" | "failed" }
```

不新增第 5 类事件：步骤是会话状态的细粒度视图，放进 `status_update` 即可，
四类事件的契约保持不变。

### 三、审批是步骤流里的一个「阻断项」

不是独立页面。清单里某一步卡住等批准，其余步骤照常显示。

## 理由

**审批是低频的，进度是高频的。**
一天可能只有三五次审批，但用户会一直想看"它跑到哪了"。高频才有留存，
低频只能做工具。

实测（opencode + ACP）证明这条数据是现成的：

```
○ 待执行   bash
● 执行中   Remove-Item -LiteralPath "data.csv"
✓ 完成     Remove-Item -LiteralPath "data.csv"
```

## 后果

- 适配器的职责变了：主要工作从"翻译审批请求"变成"翻译步骤生命周期"，
  审批只是其中一种需要停下来的步骤。
- 手机端首屏从"待审批收件箱"改为"项目进度 + 阻断项"。
- 文档里关于"AI 摘要"的描述需要清理（构想书 §3.2 四行结构要改成三行）。

## 失效条件

若将来需要跨会话的完整步骤树（比如多 Agent 协作的任务分解），
再把 `step` 提升为独立事件类型，那时是一次破坏性变更，需升版本号。
