# ADR-0005：传输与判定的三条硬规矩

- 状态：已采纳
- 日期：2026-11-06

## 背景

做前端之前，有三个决定被反复用到、但没单独记过。它们不是"实现细节"，
而是**换掉任何一层都还得成立的约束**。写下来，免得下一个会话重新发明。

## 决定一：一个 HTTP 端口同时承载页面和 WebSocket

**做法**：`http` 服务在 `/` 返回页面、在 `/health` 返回状态，`ws` 挂在同一个
服务上（路径 `/ws`），浏览器用 `ws://` 或 `wss://` 连同一个 `location.host`。

**为什么**

- 手机只需要一个地址：扫码就是那一个 URL，不用配第二个端口。
- 局域网、Tailscale Funnel、临时隧道三种入口，**同一个地址形态**。
- 隧道只转发一个端口，少一处配置、少一处出错。

**代价**：纯静态资源没有独立 CDN；页面改成每次请求都读盘（这也顺带解决了
"改页面必须重启"的问题）。

## 决定二：屏幕画面走二进制，不走 JSON

**做法**：实时画面用 WS 的 binary frame 传 JPEG（2 fps、800 宽、质量 45），
其余消息一律 JSON。

**为什么**

- base64 进 JSON 要多 33% 体积，还要多一次解析；手机上这笔开销直接体现在卡顿。
- 浏览器侧 `Blob` + `createObjectURL` 就能显示，不需要额外库。

**代价**：协议里出现两种帧类型，客户端必须按"是不是字符串"分流。
这一条已经踩过一次坑（首帧到达即崩），所以**接收端必须容错**。

## 决定三：拿不准就拒绝，但**绝不沉默挂着**

**做法**：`adapter-base` 的 `handle()` 四步全部 fail-closed：
未连接 / 格式错 / 未知事件 / 已过期 → 一律拒绝；
但**每一条请求都必须有应答**（哪怕是拒绝或 `cancelled`）。

**为什么**

- "沉默"在协议里等于"我还在想"，在用户眼里就是"卡死"。
- 曾经因为"没有可用的 allow 选项就 return"，让 Agent 干等到天荒地老。
- 拒绝是可解释的，沉默不是。

**推论**：任何"没反应"的路径都是 bug，必须变成一句话说明原因。

## 影响

- 前端可以直接假设：**一个地址、两种帧、每条请求必有回音**。
- 新增通道（比如点击/打字）时，沿用这三条：
  同端口、能用二进制就别用 JSON、必须回执。
